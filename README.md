## Project description

`frame2frame` turns ordinary video or webcam frames into a head-relative
virtual-screen composition. It estimates one person's head pose, places a
textured plane along the estimated forward direction, projects that plane
through a camera model, and composites the result into each frame.

The central task is virtual-screen rendering. Filtering, delay alignment, and
dropout recovery maintain one aligned temporal state when observations are
noisy or briefly missing. This is an AR-style rendering prototype, not an
AR-headset integration: it does not use headset telemetry, eye gaze, SLAM, or
world anchors.

### Why virtual-screen rendering is difficult

A convincing screen must remain coherent in both space and time. The system
must:

- map backend-specific pose estimates into one renderer coordinate system;
- move orientation, position, and scale together while preserving subpixel
  projection; and
- smooth noisy observations and recover from detection gaps without losing
  frame alignment.

This is an independently rebuilt open-source version of a project first
developed during an internship; it is not affiliated with or endorsed by the
employer.

## Quick start

Clone the repository and install it in a virtual environment:

```bash
git clone https://github.com/jasperzhao05/frame2frame-virtual-screen.git
cd frame2frame-virtual-screen
python -m venv .venv
source .venv/bin/activate              # Windows: .venv\Scripts\activate
python -m pip install -e .
```

Process a video:

```bash
frame2frame --input clip.mp4 --output output/clip.mp4
```

The first MediaPipe run downloads a roughly 3.6 MB Face Landmarker asset into
`~/.cache/frame2frame`.

For a more responsive webcam preview:

```bash
frame2frame --webcam 0 --filter oneeuro --display --output output/webcam.mp4
```

`oneeuro` changes only the temporal smoothing policy; MediaPipe remains the
pose backend.

Render custom screen content:

```bash
frame2frame --input clip.mp4 --texture screen.png --output output/custom.mp4
```

Check the local installation without downloading a model or opening a camera:

```bash
frame2frame --doctor
```

The command checks nine environment requirements and prints a terminal report;
it does not create a file.

## Research

### Measuring Screen Age

Temporal smoothing can suppress visible jitter while making the rendered screen
represent an older orientation. **Screen Age** measures that shift in projected
geometry by matching the filtered screen to counterfactual screens built from
earlier ground-truth attitudes while holding the current center and scale
fixed.

[![A real-person projected-screen worldline beside a compact calibration plot of analytic FIR delay against recovered Screen Age](https://raw.githubusercontent.com/jasperzhao05/frame2frame-virtual-screen/main/docs/screen-age.png)](https://github.com/jasperzhao05/frame2frame-virtual-screen/blob/main/docs/screen-age.svg)

*Projected Screen Chronometry. Panel A is a project-authored illustration over
a real AR frame: it visualizes what the default FIR's 11-frame Screen Age—367
ms at 30 fps—means; it is not a measurement from that clip or Rokid device
output. Panel B provides the calibration result: across 45 continuous BIWI
segments from 20 subjects, all six linear-phase FIR designs recover their
analytic 7-, 11-, or 19-frame delay in both the development estimate and
held-out diagnostic. Screen Age is not device or end-to-end latency.*

*Frame source: BooredAtWork's
[Rokid review](https://www.youtube.com/watch?v=abE88Vve0o4),
[CC BY 3.0](https://creativecommons.org/licenses/by/3.0/); project-authored
explanatory overlays. BIWI contributes aggregate calibration values only, and
no BIWI participant imagery is redistributed. No affiliation or endorsement is
implied.*

Read the [Screen Age protocol and aggregate calibration receipt](https://github.com/jasperzhao05/frame2frame-virtual-screen/blob/main/docs/SCREEN_AGE.md)
for the formal definition, split discipline, bootstrap audit, and scope limits.

### Deterministic filter reference

A separate seeded synthetic workload asks a different question: how much
pose-signal jitter does each filter remove while preserving the intended
motion? It does not use BIWI footage or a pose model.

```bash
python -m scripts.benchmark_smoothing --check
```

Default results at 30 fps (seed `20260730`):

| Filter | Jitter RMS | Jitter reduction | Step-response delay | Aligned RMSE |
|---|---:|---:|---:|---:|
| none | 1.329° | 0.0% | 0 frames | 0.000° |
| FIR | 0.383° | 71.2% | 11 frames / 366.7 ms | 0.072° |
| One Euro | 0.867° | 34.7% | 0 frames in this test | 0.387° |

Step-response delay is the time to reach 50% of a scripted pose step, not
end-to-end latency.

These values describe one fixed model-free workload, not universal backend
accuracy, real-footage quality, end-to-end latency, or production readiness.
Read the [benchmark protocol](https://github.com/jasperzhao05/frame2frame-virtual-screen/blob/main/docs/BENCHMARKS.md) before comparing changes.

## System design

```text
Video / webcam
      ↓
Decode + pose estimation
      ↓
Aligned temporal state
filter · alignment · hold / fade / reset
      ↓
Head-relative plane + camera projection
      ↓
Composite video / live preview
```

Orientation, face center, and apparent scale advance on the same timeline.
Brief detection gaps hold and fade the screen; sustained gaps begin a new
tracking segment before reacquisition.

The [architecture notes](https://github.com/jasperzhao05/frame2frame-virtual-screen/blob/main/docs/ARCHITECTURE.md) define coordinate conventions,
temporal invariants, resource ownership, and extension boundaries.

## Validation

The repository keeps operational checks separate from pose-accuracy and
perceptual claims.

Run the complete deterministic file pipeline and gate frame conservation,
dropout reset behavior, and repeated decoded-pixel stability:

```bash
python -m scripts.benchmark_pipeline --check
```

Create a checksum-pinned real-video receipt for the primary MediaPipe + FIR
path:

```bash
python -m scripts.fetch_examples --download-only --limit 1
python -m scripts.validate_real_video \
  --input examples/inputs/head-pose-face-detection-female.mp4 \
  --output output/real-video-validation.mp4 \
  --receipt output/real-video-validation.json
```

These checks record exact frame handling, configuration, media hashes,
observation coverage, and run timings. They do not establish pose accuracy,
camera-to-display latency, perceptual quality, or a production SLO. See the
[reliability protocol](https://github.com/jasperzhao05/frame2frame-virtual-screen/blob/main/docs/RELIABILITY.md) and
[real-video receipt protocol](https://github.com/jasperzhao05/frame2frame-virtual-screen/blob/main/docs/VALIDATION.md).

## Backends and filters

| Backend | Install | Pose source | Intended use |
|---|---|---|---|
| `mediapipe` | included by default | Face Landmarker + canonical-face PnP | Primary maintained/default adapter; validate on target footage and hardware |
| `hopenet` | `pip install -e ".[hopenet]"` | ResNet-50 binned Euler regression | Research checkpoint-compatibility adapter; paper metrics are not reproduced here |
| `6drepnet` | manual, isolated setup only | Continuous 6D rotation representation | Experimental third-party compatibility adapter; isolated setup required |

6DRepNet's published package conflicts with MediaPipe's OpenCV provider, so the
project deliberately does not advertise a one-command extra for it. Hopenet's
first run downloads a pinned 95,924,799-byte checkpoint.

MediaPipe is the default because it is the primary dependency-complete and
maintained path, not because this repository establishes superior accuracy.
Deterministic CI does not run real pose-model inference; every backend requires
validation on the intended footage and hardware.

- **`fir`** — default fixed-delay filter for offline processing; file rendering
  can compensate its known group delay.
- **`oneeuro`** — lower-filter-lag option for live preview; no end-to-end webcam
  latency claim is made.
- **`none`** — diagnostic baseline for observing detector noise.

## Known limits

This is a local research renderer, not a hardened desktop application, hosted
service, biometric system, or safety system. Public demos and validation
receipts are scoped examples rather than general guarantees.

- One face is tracked; identity association and multi-face rendering are not
  implemented.
- Camera intrinsics default to `focal = max(width, height)` unless supplied;
  face-size depth remains an approximation.
- Rotation is filtered as Euler-angle streams; extreme poses near gimbal lock
  remain a limitation.
- OpenCV writes constant-frame-rate video with a portability-oriented `mp4v`
  codec. Audio is omitted unless `--preserve-audio` is used.
- The system estimates head orientation, not eye gaze, identity, attention,
  intent, or medical state.
- Optional deep backends need more cross-device and real-footage validation
  than the default MediaPipe path.

## Repository guide

```text
frame2frame/
  pose/         pose contracts and backend adapters
  filters.py    FIR and One Euro filters
  _tracking.py  temporal alignment and dropout state
  geometry.py   camera math and screen projection
  render.py     perspective warp and compositing
  pipeline.py   end-to-end orchestration
scripts/        reproducible demos, benchmarks, and receipts
tests/          unit, invariant, integration, packaging, and CLI tests
docs/           architecture, protocols, usage, privacy, and validation
```
